## 3. State อยู่ที่ไหน ทำไม

### (ก) ทำไมคำค้นและธาตุอยู่ใน URL ไม่ใช่ `useState`

คำค้นกับธาตุเป็น "สิ่งที่ผู้ใช้กำลังดูอยู่" ไม่ใช่ข้อมูลภายในของคอมโพเนนต์ เมื่อเก็บไว้ใน query string
ด้วย `useSearchParams` ผู้ใช้จะได้ 3 อย่างที่ `useState` ให้ไม่ได้

1. **ลิงก์แชร์ได้** — copy `/pokemon?q=saur&type=grass` ส่งให้เพื่อน เปิดแล้วเห็นผลลัพธ์เดียวกันทันที
   เพราะช่องค้นหาและ dropdown อ่านค่าจาก URL โดยตรง ถ้าใช้ `useState` state จะเริ่มจากค่าว่างเสมอ
2. **ปุ่ม back ของเบราว์เซอร์ทำงานถูกต้อง** — การกรองกลายเป็นประวัติการเข้าชม และเราใช้
   `setSearchParams(next, { replace: true })` ตอนพิมพ์ เพื่อไม่ให้ทุกตัวอักษรกลายเป็น history entry
   กด back ครั้งเดียวจึงออกจากการค้นหาได้ ไม่ใช่ถอยทีละตัวอักษร
3. **refresh แล้วไม่หาย** — สถานะการกรองอยู่ใน URL ไม่ได้อยู่ในหน่วยความจำของหน้า

และเพราะ URL เป็นแหล่งความจริงเพียงที่เดียว จึงไม่มี `useState` ซ้ำที่ต้องคอย sync ให้ตรงกัน
ซึ่งเป็นจุดที่ bug มักเกิด

### (ข) ทำไมทีมหยุดที่ Context

ไล่ตาม decision framework ของวันที่ 5:

1. **`useState` ในหน้าเดียว — ไม่พอ** เพราะทีมถูกใช้อย่างน้อย 4 ที่: `Nav` (ตัวเลข n/6),
   `Home` (จำนวนสมาชิก), `PokemonCard` (ป้าย "อยู่ในทีม"), `PokemonDetail` (ปุ่มเพิ่ม/เอาออก) และ `Team`
2. **Lift state up — ไม่พอ** ถ้ายกขึ้นไปไว้ที่ `App` ก็ต้องส่ง props ผ่าน `Layout` → `Nav` และ
   ผ่านทุกหน้าลงไปถึง `PokemonCard` ทั้งที่ชั้นกลางไม่ได้ใช้ค่าเลย (prop drilling)
   ยิ่งกว่านั้นหน้าต่าง ๆ ถูกเรนเดอร์ผ่าน `<Outlet />` ของ React Router จึงส่ง props ตรง ๆ ไม่ได้อยู่แล้ว
3. **Context — พอดี** ทีมเป็น global state ก้อนเล็ก (อาเรย์ไม่เกิน 6 ตัว) เปลี่ยนไม่บ่อย
   (เฉพาะตอนกดเพิ่ม/เอาออก) และมี action แค่ `add` / `remove` / `clear` ทุกคนอ่านผ่าน `useTeam()` ทางเดียว
4. **Redux/Zustand — เกินจำเป็น** โจทย์นี้ไม่มี state ที่ซับซ้อนพอจะคุ้มกับ boilerplate ของ store,
   ไม่มี async flow ที่ต้องจัดการ, ไม่มีปัญหา performance จากการ re-render (ค่าเปลี่ยนนาน ๆ ครั้ง)
   และไม่ต้องการ devtools/time-travel ประโยชน์ที่ได้จึงไม่คุ้มกับ dependency ที่เพิ่มเข้ามา

ค่าที่คำนวณได้อย่าง `count`, `isFull`, `has(id)` เราคำนวณตอน render จาก `team` โดยตรง
ไม่เก็บเป็น state แยก เพราะ state ซ้ำซ้อนมีโอกาสไม่ตรงกับความจริง ส่วนการอัปเดตใช้รูปแบบ immutable
(`[...prev, x]`, `.filter()`) เพื่อให้ React รู้ว่าค่าเปลี่ยนและ re-render

### (ค) `memo` / `useMemo` / `useCallback` — หรือเหตุผลที่ไม่ใช้

**ไม่ได้ใช้เลย** เพราะยังไม่จำเป็นกับแอปขนาดนี้:

- งานที่หนักที่สุดคือการ `.filter()` อาเรย์ 151 ตัวตอนพิมพ์ค้นหา ซึ่งเป็นหลักไมโครวินาที
  ต่ำกว่าเวลาที่เบราว์เซอร์ใช้วาดหน้าใหม่มาก การใส่ `useMemo` จะเพิ่มโค้ดและ dependency array
  ที่ต้องดูแล แลกกับกำไรที่วัดไม่ได้
- `PokemonCard` ไม่ได้ทำงานหนัก การ re-render 151 ใบยังเร็วกว่า 1 เฟรม
- `useCallback` จะมีประโยชน์ก็ต่อเมื่อส่งฟังก์ชันไปให้ลูกที่ห่อด้วย `memo` ในเมื่อไม่มี `memo`
  การใส่ `useCallback` ก็เป็นแค่ต้นทุนเปล่า ๆ
- นอกจากนี้ค่าใน Context เปลี่ยนเฉพาะตอนกดเพิ่ม/เอาออกทีม ซึ่งเกิดไม่บ่อย

หลักที่ยึดคือ optimize เมื่อวัดแล้วพบว่าช้าจริง ถ้าในอนาคตรายการโตเป็นหลักพันตัว
จุดแรกที่จะแก้คือ `useMemo` ครอบผลการกรอง และ `memo` ที่ `PokemonCard` คู่กับ `useCallback`
