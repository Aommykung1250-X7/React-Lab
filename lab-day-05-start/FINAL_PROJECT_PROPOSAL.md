## 1. แอปนี้ทำอะไร ใครใช้

เว็บบอร์ดหาคนติวและเพื่อนอ่านหนังสือสำหรับนักศึกษา CAMT ผู้ใช้สร้างประกาศระบุวิชา
หัวข้อที่อยากเรียน ช่วงเวลาที่สะดวก และรูปแบบการนัดพบได้ ปัจจุบันประกาศลักษณะนี้กระจายอยู่ตามแชต
ทำให้ค้นหาคนที่เรียนวิชาเดียวกันและย้อนดูประกาศเก่าได้ยาก

## 2. หน้าที่จะมี (อย่างน้อย 4 route)

| Route         | หน้านี้ทำอะไร                                                               |
| ------------- | --------------------------------------------------------------------------- |
| /             | หน้าแรก — อธิบายวิธีใช้ แสดงประกาศล่าสุด และลิงก์ไปหน้าค้นหา               |
| /posts        | รายการประกาศทั้งหมด — ค้นหาตามคำและกรองตามวิชา/รูปแบบการนัดพบ              |
| /posts/[id]   | รายละเอียดประกาศ — หัวข้อ วันเวลาที่สะดวก และช่องทางติดต่อเจ้าของประกาศ      |
| /post         | ฟอร์มสร้างประกาศ — เลือกวิชา ระบุหัวข้อ รายละเอียด เวลา และช่องทางติดต่อ     |
| /saved        | ประกาศที่บันทึกไว้ — กลับมาดูประกาศที่สนใจได้ภายหลัง                         |
| /register     | สมัครสมาชิก — กรอกชื่อ อีเมล และรหัสผ่าน เพื่อสร้างบัญชีผู้ใช้                 |
| /login        | เข้าสู่ระบบ — กรอกอีเมลและรหัสผ่านเพื่อใช้งานบัญชีเดิม                         |

## 3. Server หรือ Client — และทำไม

โปรเจกต์จะใช้ Next.js App Router โดยให้หน้าที่อ่านข้อมูลเป็น Server Component และแยกส่วนที่ผู้ใช้ต้องโต้ตอบเป็น Client Component

| ส่วนของแอป                  | Server / Client | เหตุผล                                                                  |
| --------------------------- | --------------- | ----------------------------------------------------------------------- |
| หน้าแรก `/`                 | Server          | ดึงประกาศล่าสุดจากฐานข้อมูลมาแสดงตั้งแต่เปิดหน้า                         |
| รายการประกาศ `/posts`       | Server          | อ่านคำค้นและตัวกรองจาก URL แล้วดึงเฉพาะประกาศที่ตรงเงื่อนไขจากฐานข้อมูล |
| ช่องค้นหาและตัวกรอง         | Client          | รับการพิมพ์และการเลือกของผู้ใช้ แล้วอัปเดตคำค้นใน URL                    |
| รายละเอียด `/posts/[id]`    | Server          | ดึงข้อมูลประกาศตาม `id` จากฐานข้อมูลก่อนแสดงหน้า                        |
| ปุ่มบันทึกประกาศและ `/saved` | Client          | ต้องตอบสนองต่อการกดและอ่าน/เขียน `localStorage` ในเบราว์เซอร์          |
| ฟอร์ม `/post`               | Client          | รับข้อมูลจากผู้ใช้และแสดงข้อผิดพลาดของแต่ละช่องขณะกรอก                  |
| ตัวบันทึกประกาศลงฐานข้อมูล  | Server Action   | ตรวจสอบความถูกต้องอีกครั้งและเขียนลง Supabase โดยเก็บโค้ดเชื่อมต่อฐานข้อมูลไว้ฝั่งเซิร์ฟเวอร์ |
| ฟอร์ม `/register` และ `/login` | Client        | รับข้อมูลบัญชีและแสดงสถานะกำลังทำงานหรือข้อผิดพลาดจากการยืนยันตัวตน     |
| การสมัคร/เข้าสู่ระบบ/ออกจากระบบ | Server Action / Supabase Auth | ตรวจสอบข้อมูลบัญชีและจัดการ session ผ่าน Supabase Auth โดยไม่เก็บรหัสผ่านในแอป |
| root layout                 | Server          | แสดงโครงหน้าและครอบหน้าด้วย Client Provider สำหรับ global state             |
| navigation และเมนูผู้ใช้    | Client          | อ่าน global state เพื่อแสดงลิงก์เข้าสู่ระบบ หรือชื่อผู้ใช้และปุ่มออกจากระบบ   |

### Global state

- ใช้ `AuthContext` ผ่าน React Context Provider ใน root layout เป็น global state สำหรับ session, ข้อมูลผู้ใช้ปัจจุบัน และสถานะการโหลด/ยืนยันตัวตน เพื่อให้ navigation และหน้าที่ต้องรู้สถานะผู้ใช้เข้าถึงข้อมูลเดียวกันได้
- ใช้ `SavedPostsContext` สำหรับรายการ `id` ของประกาศที่ผู้ใช้บันทึกไว้ เพื่อให้ปุ่มบันทึกและหน้า `/saved` แสดงข้อมูลตรงกันทุกหน้า และ sync กับ `localStorage` ในเบราว์เซอร์
- Server Component อ่าน session จาก cookie ผ่าน Supabase SSR เมื่อต้องตรวจสิทธิ์หรือโหลดข้อมูลเฉพาะผู้ใช้ ส่วน Client Component อ่านสถานะจาก Context; เมื่อเข้าสู่ระบบหรือออกจากระบบให้ refresh ข้อมูล session
- ผู้ใช้ที่ยังไม่เข้าสู่ระบบดูและค้นหาประกาศได้ แต่ต้องเข้าสู่ระบบก่อนสร้างประกาศหรือบันทึกรายการ

## 4. ข้อมูลมาจากไหน + จุดที่ต้องเขียนข้อมูลกลับ

- แหล่งข้อมูล: Supabase Auth จัดการบัญชีและ session; ตาราง `user_profiles` เก็บชื่อที่แสดงและเชื่อมกับผู้ใช้; ตาราง `study_posts` เก็บวิชา หัวข้อ รายละเอียด รูปแบบการนัดพบ เวลาที่สะดวก ช่องทางติดต่อ วันเวลาที่สร้างประกาศ และ `author_id` ที่อ้างถึงเจ้าของประกาศ ส่วนรายการที่บันทึกไว้เก็บ `id` ใน global state และ sync กับ `localStorage` ของผู้ใช้
- mutation (Server Action / Route Handler) ที่จุดไหน: `registerUser` และ `loginUser` เรียก Supabase Auth สำหรับสมัครและเข้าสู่ระบบ; `logoutUser` ใช้จบ session; `createStudyPost` รับข้อมูลจากฟอร์ม `/post` ตรวจสอบ session และข้อมูลอีกครั้งก่อนสร้างรายการใน `study_posts` โดยบันทึก `author_id` ของผู้ใช้ที่เข้าสู่ระบบ แล้วอัปเดตรายการใน `/posts`
- การเผยแพร่: deploy แอปบน Vercel และเชื่อมต่อฐานข้อมูล Supabase ผ่าน environment variables

## 5. แบ่งงานกันยังไง

- ภานุวัฒน์: หน้าแรก, `/posts`, ระบบค้นหา/กรอง, การอ่านข้อมูลจาก Supabase, Supabase Auth และ global state สำหรับ session/ผู้ใช้ รวมถึง deploy บน Vercel
- สุวรรณชัย: `/posts/[id]`, ฟอร์ม `/post` พร้อม validation, `/saved` และ global state สำหรับรายการที่บันทึกไว้, หน้า `/register` และ `/login` พร้อมปรับหน้าเว็บให้ใช้ได้บนมือถือ
